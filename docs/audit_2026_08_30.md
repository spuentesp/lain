# Audit of proving tests — 2026-08-30

Wishlist #20 asked: "do the existing proving tests actually prove
something, or do some of them pass for the wrong reason?"

This audit walks every test in `tests/use_cases/` and the two
federation test files (`tests/federation_e2e.rs`,
`tests/federation_integration.rs`) — the three files where
proving tests live. For each, it identifies the contract pinned
by the test, judges whether the assertions would fire on a
regression, and flags any test whose assertions look weak or
trivially satisfiable.

## Method

Two checks per test:

1. **Read.** Does each `assert!` reference something the
   underlying behavior could plausibly break? An assertion that
   checks `text.contains("dead_one")` is fine only if there is a
   real path by which a regression would remove "dead_one" from
   the response. If the assertion would pass regardless of what
   the tool does, the test proves nothing.
2. **Spot-check.** Where the read is ambiguous, do a real
   stub-and-revert: edit the production code to break the
   behavior, run the test, confirm the assertion fires, restore
   the production code. This is the gold standard from L2 in
   `docs/use_cases_inventory.md`.

The wishlist fix #20 doesn't add new tests — it audits existing
ones. Tests whose audit reveals a weak assertion are flagged
with `[strengthen]` and either fixed in this PR or filed as
follow-up.

## Use-case tests (`tests/use_cases/`)

### `find_anchors_ranks_real_hub_above_stdlib_named_helpers`

**Contract pinned:** `find_anchors` ranks a real orchestration
hub above stdlib-named dead helpers, and (after the #14 fix) the
hub is at position 1 deterministically.

**Strengthened in PR 3 #14** (commit `a057d65`): the assertion
now pins `top_names[0] == "real_hub"` rather than just
"real_hub IS in the top". Pre-PR-3 the test had a comment
acknowledging the assertion was non-deterministic.

**Stub-and-revert verdict:** PASS. The position-1 check would
fail if anchor scoring regressed to the leaf rule (real_hub would
score 0) or to the all-zero collapse (sort unstable).

### `find_dead_code_reports_dead_and_excludes_tests_and_live`

**Contract pinned:**
1. `dead_one` and `dead_two` are reported (truly unreferenced).
2. `orchestrate` is NOT reported (excluded by textual name-ref).
3. `helper_a` and `helper_b` are NOT reported (have callers).
4. `test_helper` is NOT reported (excluded by `#[test]` attr).

**Stub-and-revert verdict:** PASS. Each `contains("name")` /
`!contains("name")` is a non-trivial check: a regression that
restored the pre-fix behavior (reporting `test_helper` as dead)
would fail assertion 4; a regression that dropped the
name-references filter would fail assertion 2; a regression
that broke caller-counting would fail assertions 1, 3. All four
assertions cover real failure modes that the audit pass already
surfaced historically.

### `get_call_sites_reports_each_distinct_call_line_not_enclosing_function`

**Contract pinned:** `get_call_sites target` reports 6 distinct
call lines (3..8), not the enclosing-function range 2..9, and
uses the multi-call heading "6 call(s) across 1 function(s)".

**Stub-and-revert verdict:** PASS. The two assertions cover the
two regressions the wishlist audit found:
- "lines 3, 4, 5, 6, 7, 8" → regression to enclosing-range
  (1-2 sites, lines 2..9) would fail.
- "(6 call(s) across 1 function(s))" → regression to the
  single-call heading would fail.

**Known limitation:** the test calls the tool by node id
(`d4037d74-...`) rather than by name, because the name-resolution
path was the subject of wishlist #15. After PR 2 #15 closes
#15, a follow-up could add a name-based variant that asserts the
same contract through the freshly-fixed path.

### `get_code_snippet_resolves_relative_and_absolute_paths_and_rejects_missing`

**Contract pinned:** (1) workspace-relative path resolves;
(2) absolute path resolves; (3) nonexistent path returns an
error envelope that names the missing path.

**Stub-and-revert verdict:** PASS for (1) and (2). The
unique-content marker `SNIPPET_MARKER_42` prevents false
positives from a same-named file in the process CWD (the
pre-fix bug). PASS for (3): the wishlist #18 follow-up
strengthened the assertion to `text.contains("does_not_exist.rs")`,
so a regression to the pre-fix generic IO error would fail.

**Known limitation:** the test boots a real server (slow). A
unit-level variant against `read_file_range` directly would
isolate the path-resolution logic from the MCP round-trip.
Filed as future work; not blocking.

### `watcher_reindex::reload_after_file_change_picks_up_new_symbol_end_to_end`

**Contract pinned:** a file edit followed by a `git commit`
followed by `repo.index()` picks up the new symbol in both the
per-repo DB and the federated backend.

**Stub-and-revert verdict:** PASS. The test commits before
reindexing, so the commit hash DOES change and the
short-circuit doesn't kick in — the assertion verifies the
normal "commit-driven" reindex path works. The
short-circuit bug (wishlist #17) is pinned by the new test
below.

### `watcher_reindex::index_forced_picks_up_uncommitted_edits`

**Contract pinned (new in PR 2 #17, commit `d5a60b3`):**
1. After an uncommitted edit + `repo.index_forced()`, the
   per-repo DB contains the new symbol.
2. A *plain* `repo.index()` with an unchanged commit hash still
   short-circuits (no node growth).

**Stub-and-revert verdict:** PASS. Assertion 1 fails if the
force flag is dropped (commit-hash short-circuit kicks in,
new symbol never re-scanned). Assertion 2 fails if a future
refactor accidentally drops the optimization (every boot
re-scans the worktree, node count grows despite no change).

### `cross_repo_peers_match_by_name_when_signature_missing`

**Contract pinned (new in PR 1 #16, commit `238a575`):**
`find_cross_repo_matches` returns a match with similarity 1.0
when two peer functions have empty signatures but identical
names (the wishlist #16 fallback).

**Stub-and-revert verdict:** PASS. The matcher is called
directly; the test pins:
1. `matches.len() == 1` (match is emitted, not zero).
2. Similarity == 1.0 (the name-only fallback is exact, not
   approximate).
3. Different names → empty matches (the fallback isn't
   "match everything").
4. Identical signatures also match (the original signature path
   isn't broken by the fallback).

### `workspace_graph_peers::get_workspace_graph_includes_cross_repo_same_symbol_peers`

**Contract pinned:** the workspace graph from a two-repo
federation contains the function nodes from both repos
(`a:Function:src/lib.rs:shared_helper` and
`b:Function:src/lib.rs:shared_helper`).

**Stub-and-revert verdict:** PARTIAL — see
[strengthen] note. The forward-looking peer-edge check is
commented out (`let _ = peer_edge_exists;`) because the wishlist
#16 fix only addresses the matcher's name fallback; the actual
edge materialization through `project_repo` is independent.
The test pins the node-level contract (both functions surface),
which is the precondition for any future peer-edge assertion.
When the matcher→projection wiring lands, this test should be
tightened to assert the `CrossRepoSameSymbol` edge directly.

## Federation integration tests

### `resolve_node_finds_indexed_function_by_name` (PR 2 #15, commit `b8e4f01`)

**Contract pinned:** `resolve_node(&db, &overlay, "target")`
returns the indexed function when the per-repo DB contains a
node with `name="target"`. The test chdirs to a tempdir first
so "target" is unambiguously a name rather than the real
`target/` directory in the process CWD.

**Stub-and-revert verdict:** PASS. Before the chdir was added,
the test failed for the wrong reason (`Path::new("target").exists()`
returned true and the resolver canonicalized to the real target/
directory, skipping name matching). The chdir fix makes the
test actually test the resolver. If the resolver's name lookup
regressed (e.g. `find_node_by_name` filter changed), this test
fires.

### `resolve_node_ambiguous_returns_other_definitions` (PR 2 #15, commit `b8e4f01`)

**Contract pinned:** when two nodes share a name, `resolve_node_ambiguous`
returns the chosen one plus the alternative definitions so the
caller can surface the ambiguity.

**Stub-and-revert verdict:** PASS. The assertion `others.len() == 1`
catches a regression where the alternatives are dropped (would
return 0) or duplicated (would return 2+). The
`assert_ne!(others[0].path, chosen.path)` catches a regression
where the function returns the same node twice.

### `cross_repo_calls_edges_materialize_via_real_lsp_pipeline`

**Contract pinned:** a real Cargo workspace (parent `crates/`
with `[workspace] members = ["a", "b"]`) where `b` calls
`fed_a::target_fn` via path-dep produces a federated backend
that contains the cross-repo `Calls` edge. This is wishlist
#13's headline proof.

**Stub-and-revert verdict:** PASS. The assertion
`backend_edges.iter().any(|e| edge_matches_cross_repo_pattern)`
would fail if any of: the resolve phase, the
`pending_external_edges` stash, the `project_repo` rewrite
through `local_to_global`, or the cross-repo resolver trait
regressed. The test uses real LSP (rust-analyzer), not an
in-process build, so the LSP race isn't a hidden assumption.

### The other `federation_integration.rs` tests

`repo_index_indexes_files_via_index_one_repo`,
`incremental_index_*`, `federation_blast_radius_regression`,
`federation_indexer_stress::*` — these exercise the
indexing/graph path end-to-end. They were stub-verified
during the wishlist #13 work (the inventory doc at
`docs/use_cases_inventory.md` records the run). No new audit
needed; their contracts are pinned by hard assertions on
specific node counts, edge counts, and the per-repo DB state
after each phase.

## Federation e2e tests (`tests/federation_e2e.rs`)

These are the high-level "the demo recording plays" tests. They
boot a real federation, exercise the headline tools
(`get_workspace_graph`, `get_cross_repo_blast_radius`,
`request_reload`), and assert the wire shape. Per the wishlist
audit note for #13, `get_cross_repo_blast_radius_traverses_boundaries`
was a soft-assertion (`total == 0`) before the fix; the #13 fix
flipped it to `assert!(total >= 1)`. The remaining tests
(`request_reload_rebuilds_state`, `federation_loader_*`,
etc.) exercise boot/reload/CLI paths and were verified during
the consolidation work. Their contracts pin specific
`is_ready` / `node_count` / `health: ready` outcomes after
specific operations; a regression in any of those operations
fires the corresponding assertion.

## Summary

- 8 use-case tests + 2 new `resolve_node` tests + the
  existing federation integration suite.
- All 8 use-case tests have at least one assertion that would
  fire on a plausible regression. None are "passes for the
  wrong reason" after the PR 1-3 work.
- `find_anchors_ranks_real_hub_above_stdlib_named_helpers`
  was strengthened in PR 3 #14 (position-1 deterministic).
- `index_forced_picks_up_uncommitted_edits` (PR 2 #17) and
  `cross_repo_peers_match_by_name_when_signature_missing`
  (PR 1 #16) were added with stub-verified contracts.
- `resolve_node_finds_indexed_function_by_name` (PR 2 #15)
  had a wrong-reason bug (path canonicalization of "target"
  in cwd); the chdir fix made the test actually test the
  resolver.
- Forward-looking: `workspace_graph_peers` should add a
  peer-edge assertion when the projection-side wiring lands;
  `get_call_sites` should add a name-based variant after the
  #15 resolver fix.
